# Переход на Material 3 — как

> Решение: vault `decisions/android-is-material-3.md`. Правила дизайна: `AGENTS.md` → Design System.
> **Состояние здесь не ведётся** — только в `IMPLEMENTATION_PLAN.md`, направление C6. Этот файл
> отвечает на «как и в каком порядке», и меняется, только если меняется порядок.

## Что значит «без потерь»

Потерять при переходе можно четыре вещи; каждой назначен свой сторож:

| Что можно потерять | Сторож |
|---|---|
| Поведение (назад, подтверждение удаления, валидация поля, доступность) | обёртка сохраняет сигнатуру — вызывающий код не меняется; поведение компонента переносится в обёртку, а не переписывается на каждом экране |
| Внешний вид, который никто не собирался менять | скриншот-тесты превью: дифф показывает каждое изменение пикселей до мержа |
| Контраст | `CTColorContrastTest` меряет пары ролей (`primary`/`onPrimary` и т. д.), а не только CT-пары |
| Плотность и «наш» характер | шаги, которые меняют вид, отделены от шагов, которые меняют код; плотность — отдельное решение владельца (§6) |

Главный приём — **развести «меняем код» и «меняем вид».** Сначала код переезжает на Material так,
что экран не меняется ни на пиксель (это проверяемо скриншотами). Потом новый вид приходит одной
сменой значений в теме, и его дифф — ровно новый дизайн, без примеси случайных поломок.

Следствие: шаги 0–3 не ждут Figma-файла. Файл нужен только в шаге 4.

## Что есть сейчас (2026-10-08)

- `MaterialTheme` уже обёрнут вокруг приложения (`ui/theme/Theme.kt`), но схема заполнена на треть:
  10 ролей из ~35, остальные — фиолетовый baseline Material. Ни один экран не читает
  `MaterialTheme.colorScheme` — всё идёт через `CTColor` (898 обращений в 73 файлах; топ:
  `textDim` 209, `accent` 158, `text` 122, `danger` 108, `bg` 63, `noise` 48, `bgMsg` 40).
- `Typography` заполнена частично (9 из 15 ролей), `Shapes` не задана.
- Compose BOM `2024.02.00` (material3 1.2) — старый: нет актуальных `SearchBar`, `ListItem`-поведения,
  предиктивного «назад» в `TopAppBar`/шторках, Expressive-компонентов.
- Material-компоненты уже в ходу: `AlertDialog` ×7, `Switch` ×3, `DropdownMenu` ×3,
  `ModalBottomSheet` ×1, `Icon` ×72. Их сейчас красит недозаполненная схема.
- 29 файлов с `@Preview` — готовый материал для скриншот-тестов. `testTag` нет ни одного.

## Шаг 0. Подготовка — ничего не меняется на экране

1. **Обновить Compose BOM** до текущего стабильного. Отдельный PR: только версия и то, что она
   сломала при компиляции. Прогнать `--device`.
2. **Скриншот-тесты.** Плагин Compose Preview Screenshot Testing (`com.android.compose.screenshot`)
   или Roborazzi — оба чисто build-time, GMS не нужен. Снять эталоны всех превью в тёмной и светлой
   теме. Добавить превью экранов, которых нет: список чатов, чат, настройки, профиль контакта,
   онбординг, звонок — с фиктивным состоянием, без ядра.
3. **Контраст ролей.** `CTColorContrastTest` дополняется проверкой пар `ColorScheme`:
   `on*` на своей роли ≥ 4.5, `onSurfaceVariant` на `surface`/`surfaceContainer*` ≥ 4.5,
   `outline` на фоне ≥ 3.
4. **Храповик на компоненты** в `scripts/check_ui_tokens.sh`: счётчик вызовов `CTNavBar(`,
   `CTTabBar(`, `CTButton(`, `CTTextField(`, `CTSearchBar(`, `CTModeSelector(`,
   `CTConfirmDialog(`, `CTSettingsRow(`, `Construct*Row(` — может только падать.

## Шаг 1. Мост темы — роли заполнены нынешними цветами

Цель: Material и CT показывают одно и то же. Скриншоты не меняются.

Как сделано (`ui/theme/Theme.kt` → `ctColorScheme`, `Color.kt`):

1. **`ColorScheme` — все роли**, тёмная и светлая, из палитры `CTColor.…Dark/…Light`:

   | Роль Material | CT | Заметка |
   |---|---|---|
   | `background`, `surface`, `surfaceContainerLowest`, `surfaceDim`, `surfaceTint` | `bg` | плоско: оттенка на приподнятых поверхностях нет |
   | `surfaceContainerLow`, `surfaceContainer`, `surfaceContainerHigh` | `outMsgBg` | так CT красит диалоги и меню |
   | `surfaceContainerHighest`, `surfaceVariant`, `surfaceBright`, `*Container` (кроме primary) | `bgMsg` | карточка; у CT один приподнятый уровень |
   | `onBackground`, `onSurface`, `inverseSurface`, `on*Container` | `text` | |
   | `onSurfaceVariant`, `outline` | `textDim` | `outline` должен давать 3:1 к фону, `noise` не даёт |
   | `outlineVariant` | `noise` | разделители |
   | `primary` / `onPrimary` | `accent` / `bg` | как подпись `CTButton`; белый на тёмном акценте был 3.39 |
   | `primaryContainer`, `secondary` / `onPrimaryContainer`, `onSecondary` | `accentDim` / `onFill` | |
   | `tertiary` / `onTertiary` | `warning` / тёмный | не `danger`: опасность — это `error` |
   | `error` / `onError` | `danger` / `onFill` | белый на `danger` — 4.42, известно |
   | `scrim` | чёрный | Material сам кладёт 32 % |

   Без роли остаются своими токенами: пузыри (`outMsgBg`, `outMsgText`), статусы
   (`online`, `delivered`, `answer`), всё поверх медиа, QR, `scrim` приложения.
2. **`Typography`**: роли, которые экраны уже читают, не тронуты (`Text` без стиля — это
   `bodyLarge`); display и headline — размеры Material в JetBrains Mono. Подгонка `labelLarge`
   (кнопки), `titleLarge` (верхняя панель) и остальных к ролям CT — часть замены каждого
   компонента на шаге 2, где её покажет дифф скриншотов.
3. **`Shapes`** из `CornerRadius`: меню 6, чипы 8, карточки 12, крупные 16, диалоги и шторки 20.
4. **`CTColor` читает роли**: `bg`, `bgMsg`, `accent`, `accentDim`, `text`, `textDim`, `noise`,
   `danger`, `warning` — геттеры над текущей схемой; ~900 обращений не менялись.

Проверка: 72 скриншота совпали с эталонами без перезаписи. Изменились только Material-компоненты
без явного цвета, которых нет в превью: меню вложений в чате (было фиолетово-серым baseline), углы
диалогов (28 → 20) и меню. Контраст: исправлен белый на тёмном акценте; три пары `danger` ниже
4.5 (белый на нём 4.42, он как текст на светлом фоне 3.95) — их чинит значение `danger` по теме,
а это решение дизайна, не моста.

## Шаг 2. Компоненты — сначала внутренности, потом вызовы

Для каждого CT-компонента два PR:

- **2a. Обёртка на Material.** Тело `CTButton` становится `Button`/`FilledTonalButton`/
  `OutlinedButton`, сигнатура та же — все вызовы получают Material за один PR. Поведение
  компонента (destructive, disabled, кнопка «назад», подтверждение) переносится сюда и
  покрывается тестом. Скриншоты: дифф ожидаемый и смотрится один раз на всех экранах сразу.
- **2b. Разворачивание вызовов** (по экрану за коммит, фоном): вызов меняется на Material-компонент
  напрямую, где обёртка ничего не добавляет. Обёртка удаляется с последним вызовом. Где она несёт
  смысл (например, `CTConfirmDialog` = «разрушительное действие + отмена»), она остаётся
  тонкой обёрткой над Material — это нормально.

Порядок — от листьев с малым числом вызовов к каркасу экранов:

| # | Было | Станет | Вызовов | Заметки |
|---|---|---|---|---|
| 1 | `CTConfirmDialog` | `AlertDialog` | 13 | `AlertDialog` уже в ходу ×7 — свести к одному виду |
| 2 | `CTButton` | `Button` / `FilledTonalButton` / `OutlinedButton` / `TextButton` | 8 | destructive = цвета `error`; иерархию (какая кнопка главная) — спросить дизайнера |
| 3 | `CTModeSelector` | `SingleChoiceSegmentedButtonRow` | 4 | |
| 4 | `CTTextField` | `OutlinedTextField` / `TextField` | 7 | клавиатура, `visualTransformation`, ошибки; PIN-экран не трогать вслепую |
| 5 | `CTSearchBar` | `SearchBar` / `DockedSearchBar` | 5 | нужен свежий BOM |
| 6 | `CTSettingsRow`, `ConstructActionRow`, `ConstructNavRow`, `ConstructButtonRow` | `ListItem` (+ `Switch` / `Icons.Default.Check` / шеврон в `trailingContent`) | 41 | самая заметная плотность — см. §6 |
| 7 | `CTSectionGroup`, `CTSettingsSectionHeader` | `Card`/`Surface` на `surfaceContainer` + заголовок `labelLarge` | 10 + 12 файлов | `>` в заголовке секции — наш, остаётся |
| 8 | `CTSep`, `CTRowDivider` | `HorizontalDivider` (`outlineVariant`) | 35 | ASCII-разделитель — декоративный; где он хром, а не разделитель списка, оставить |
| 9 | `CTNavBar` | `TopAppBar` в `Scaffold` | 13 (18 файлов) | предиктивный «назад», `scrollBehavior`; чат с прозрачной «стеклянной» шапкой — отдельно, последним |
| 10 | `CTTabBar` | `NavigationBar` | 2 | иконки уже Material |

Не переводятся — это содержимое или наш характер, а не элементы управления; они только читают роли:
пузыри (`MessageBubble`, медиа, голосовые, видеозаметки, реакции), поле ввода чата
(`MessageInputView`), аватары и идентиконы, `CTSystemMessage` (`>`), `CTStatusBadge` (статус, уже на
Material-иконках), экраны звонка и камеры поверх картинки, QR, `CTNoise`/`CTMatrixBackground`,
`CTLogoView`. `glassCapsule` — пересмотреть вместе с шапкой чата (п. 9).

## Шаг 4. Новый вид — когда придёт Figma-файл

К этому моменту всё читает роли, поэтому смена дизайна — это **смена значений в одном файле темы**:

1. Ответы дизайнера на открытые вопросы (vault `sessions/2026-10-08-android-material-3.md`):
   шрифт Plain, фон, палитра, светлая тема, контраст черновика, недостающие роли.
2. Значения переменных Figma → `ColorScheme`/`Typography` повторяемым шагом (Figma MCP
   `get_variable_defs` или экспорт плагина `construct-design`), не перепечатыванием hex.
3. Один PR: новая тема + обновлённые эталоны скриншотов + зелёный `CTColorContrastTest`.
   Дифф скриншотов — это и есть ревью дизайна, его смотрит дизайнер.

Шаги 2 и 4 независимы: если файл придёт раньше, чем закончатся компоненты, шаг 4 можно сделать
посередине — непереведённые CT-компоненты всё равно перекрасятся через мост из шага 1.

## §6. Решения, которые нужны от владельца и дизайнера до шага 2

- **Плотность.** Material задаёт минимальную зону нажатия 48 dp, `ListItem` от 56 dp,
  `TopAppBar` 64 dp, `NavigationBar` 80 dp — заметно просторнее нынешнего CT. Зону нажатия
  уменьшать нельзя (доступность), высоту строк и панелей можно поджать. Решить: принимаем
  размеры Material или задаём свои (это часть «нашего характера» из решения).
- **Шапка и таб-бар в чате:** Material-панели непрозрачные; нынешняя «стеклянная» шапка — наша.
- **Иерархия кнопок:** какая кнопка залитая, какая тональная, какая текстовая.
- **Dynamic color (Material You):** по умолчанию выключен — он заменяет фирменную палитру.

## Как вести

- Один компонент или один экран — одна ветка `refactor/m3-<что>` и один PR в `develop`.
- В каждом PR: обновлённые эталоны скриншотов (дифф глазами), `scripts/verify.sh`; для навигации,
  полей ввода и диалогов — `--device` и ручной проход по затронутым экранам.
- Закрытый шаг отмечается в `IMPLEMENTATION_PLAN.md` (C6) в том же PR.
