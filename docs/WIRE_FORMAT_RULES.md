# Правила конверта — что Android кладёт на провод, а что нет

**Читать перед работой над путём отправки** (`SendMessageUseCase`, stealth, multi-device).

**Описание формата не здесь.** Раскладка слоёв, размеры заголовков и сводка «что видит сервер» —
`~/Code/construct-docs/architecture/WIRE_FORMAT.md`. Этот файл намеренно не пересказывает её: копия
описания, которую никто не синхронизирует, расходится с оригиналом молча. Здесь только правила,
чек-лист и тест-векторы — векторы тем и хороши, что при расхождении падают, а не врут.

---

## Зачем этот файл существует

iOS прошёл к этим правилам через ошибки, каждая из которых жила месяцами и находилась разбором
логов, а не чтением кода. Список — не гипотетический:

| что было | сколько прожило | чем кончилось |
|---|---|---|
| SENDER_SYNC маршрутизировался по `conversation_id`, который сервер обнуляет намеренно | с момента появления функции | ни одна копия своего сообщения не попала на второе устройство **ни разу** |
| тот же незапечатанный конверт нёс `direct:я:собеседник` открытым текстом | с момента появления функции | сервер получал пару собеседников в обход sealed sender, на каждое отправленное сообщение |
| `sender_device` / `recipient_device` заполнялись | всегда | сервер их не читает ни разу; отдавалась топология устройств |
| heartbeat объявлял себя типом 13 на внешнем конверте | всегда | сервер мог отличить пробы живости от переписки |
| `__session_reset_notify__` — строка без читателя | 4 месяца | писалась в переписку видимым пузырём на многоустройственных аккаунтах |

Общее у всех: **поле писалось клиентом, не читалось никем и стоило метаданных**. Ни одна из этих
ошибок не была ошибкой криптографии.

## Правила

### 1. Незапечатанный конверт не несёт ничего сверх пары отправитель/получатель

Главный инвариант. Многоустройственный трафик (SENDER_SYNC, веер по своим устройствам) намеренно
**не** запечатывается — обоснование «сервер и так знает, что это один аккаунт». Оно верно ровно для
отправителя и получателя и **неверно** для всего остального в том же конверте.

```kotlin
// НЕТ
envelope.conversationId = "direct:$myUserId:$partnerUserId"

// ДА — поле не заполняется вовсе
```

### 2. Тип содержимого — в байте 5 KNST-кадра, не в конверте

Внешний `content_type` для обычной отправки всегда обобщённый (`E2EE_SIGNAL`). Настоящий тип едет
внутри шифротекста, где сервер его не прочитает.

Исключения — **два**, и оба структурные, а не унаследованные:

| тип | почему снаружи |
|---|---|
| 21 `SESSION_RESET` (END_SESSION) | нет шифротекста, куда положить кадр |
| 24 `SESSION_RESET_INIT` | на проводе неотличим от обычного X3DH-носителя; тип нужен **до** расшифровки |

Всё остальное — 12 (сигнал звонка), 13 (heartbeat), 14 (квитанция), 23 (SENDER_SYNC), 25/26
(ping/ready) — в байте 5. Добавлять новое исключение можно только с обоснованием того же рода.

### 3. Обрамляют все производители

Любой шифруемый текст проходит через KNST-кадр — `frameWhole` для одиночного, нарезку для
длинного. Голый proto, голый UTF-8 и магические строки в качестве полезной нагрузки не отправлять.

```kotlin
// НЕТ — так iOS слал heartbeat, и строку никто не читал
plaintext = "__heartbeat__".toByteArray()

// ДА — пустое тело, тип в байте 5
plaintext = frameWhole(ByteArray(0), contentType = 13, messageId = uuid)
```

### 4. У каждого факта один носитель

- Личность отправителя — Bearer-токен. `envelope.sender` сервер читает **только чтобы отвергнуть**
  несовпадение, источником истины он не является.
- Какое устройство прислало SENDER_SYNC — **та сессия, которая его расшифровала**. Не поле, не
  заголовок. Устройство отправителя физически нельзя положить в шифротекст: оно выбирает сессию
  Double Ratchet, то есть нужно до расшифровки.
- Тип содержимого — байт 5, не `SealedInner.content_type`.

Второй носитель того же факта — это будущее расхождение. Не заводить.

### 5. Ничего не кодируется дважды

Никакого base64 в прикладной логике (только на текстовых границах: QR, deep link). Никакого JSON
для двоичного. Идентификаторы — сырыми байтами, как `message_id` в KNST-заголовке.

### 6. Производитель без читателя — дефект

Если добавляете отправку сигнала, читатель обязан появиться в том же изменении. Неиспользованное
сообщение стоит продвижения рэтчета и рано или поздно всплывает в интерфейсе.

## Чек-лист перед добавлением поля в конверт

Письменно, а не мысленно:

1. **Кто его читает?** Если сервер не читает — поле не нужно. Проверять `grep` по
   `~/Code/construct-server`, а не по названию поля в proto: объявленное ≠ читаемое.
2. **Что оно сообщает серверу о том, кто с кем общается?** Если что-то — место поля внутри
   шифротекста.
3. **Есть ли уже носитель этого факта?** Если да, использовать его, а не добавлять второй.

## Что Android должен реализовать точно

### Доставка идёт всему пользователю, а не устройству

`messaging-service/src/core.rs` берёт устройства получателя из базы (`fetch_recipient_device_ids`)
и пишет **один и тот же конверт** в каждую per-device очередь. Значит:

- `recipient_device` в конверте бессмысленен — не заполнять;
- каждое устройство получает копии, предназначенные другим устройствам того же аккаунта, и
  расшифровать их не может. Отбрасывать их **до** попыток расшифровки, по тегу в идентификаторе
  сообщения (см. ниже), иначе каждая чужая копия прогонит весь перебор сессий и на первом
  сообщении полезет за ключевым пакетом в сеть.

### SSR1 — заголовок маршрута для SENDER_SYNC

Появился в iOS 0.18.0. Копия размещается, только когда **обе** стороны его понимают.

Раскладка и обоснование:
`~/Code/construct-docs/decisions/sender-sync-routing-inside-the-ciphertext.md`.

Кладётся **до** нарезки на чанки, снимается **после** сборки и **до** разбора содержимого.

**Тест-векторы** (проверять ими, а не глазами):

```
partnerUserId = "7574fdec-ca31-44ac-9d43-0e6e870fe4d5"
header (hex)  = 53535231 7574fdec ca3144ac 9d430e68 70fe4d5   ← "SSR1" + 16 байт UUID
длина         = 20

partnerUserId не UUID  → заголовок НЕ строится, отправка без него
заголовок из нулевого UUID → отвергается на приёме (иначе все повреждённые
                             копии сойдутся в один фантомный диалог)
отсутствие магии "SSR1" → отправитель на старой сборке, копию не размещать
```

### Идентификатор SENDER_SYNC на проводе

```
<uuid>-ss-<tag>          одиночный чанк
<uuid>-ss-<tag>-c<n>     чанк n из нескольких
```

`tag` — **первые 8 символов** идентификатора устройства-получателя. Сравнение с собственным
устройством — по префиксу, не на равенство: полное равенство не совпадёт никогда, и тогда
отбрасываются **все** копии, включая свои. Это ровно та ошибка, которую iOS поймал мутационным
тестом, а не глазами.
